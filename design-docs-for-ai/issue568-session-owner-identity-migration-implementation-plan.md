# Issue #568 — Session identity の owner 対応に向けた既存データ移行

対象: https://github.com/shin902/my-discord-agent/issues/568 （コメントなし、2026-09-29取得）。本計画は Bot 指定 cron を実装しない。Group 別 SQLite の論理 identity を `(agent_id, id)` とする保存構造への一回限りの移行と、現行経路の更新に限る。既存 Main の `id`（Discord channel/thread ID を含む）は変更せず、通常会話と destination cron の混在履歴も分割しない。既存 Bot Task Session も破壊しない。queue の owner 別順序、返信ルーティング、複数 owner 同一 ID の実行経路と受入テストは #565 以降。

## 現状と採用する物理方式

- `src/agent/session.ts`: schema v5。`sessions(id TEXT PRIMARY KEY, kind, created_at, updated_at, agent_id)` と `session_entries(id INTEGER PRIMARY KEY AUTOINCREMENT, session_id REFERENCES sessions(id) ON UPDATE CASCADE ON DELETE CASCADE, sequence, entry_type, payload_json, created_at, source_json)`。`readConversations()` は entry の整数 ID によって `committed_conversations` を引く。`appendMessage()` の `agentId` は現状末尾 optional 引数で default `main`; 既存 session への conflict update は owner を変えない。`renameSession()` は同じ DB の entry 所属を CASCADE で保つ。
- `src/queue/repository.ts`: runtime DB の `jobs.session_id` は順序キー、`jobs.payload_json` に sessionId、`jobs.conversation_path` は診断用 locator。`committed_conversations` は group と user/assistant entry 整数 ID を保持し session ID を持たない。runtime DB の参照・ID を変換しないことが今回の互換条件。
- **選択: 複合 PRIMARY KEY `(agent_id, id)` と複合 FK `(agent_id, session_id)`**。既存の `session_entries.id` をそのまま維持でき、余分な内部 session key とマッピングを作らない。`session_entries` に `agent_id TEXT NOT NULL`（新規列）を追加し、`sessions.agent_id, sessions.id` を同じ順序で参照する。既存の `session_entries.id`, `sequence`, `payload_json`, `source_json`, timestamp を一切再採番・再生成しない。`UNIQUE(agent_id, session_id, sequence)` とする。新規 DB 作成も同じ schema v6 に統一する。
- SQLite の `foreign_keys=ON` は接続ごとに設定する。親 ID rename は同じ owner に限定し複合 FK の `ON UPDATE CASCADE` を使う。`readConversations()` の user/assistant JOIN は両 entry の `agent_id` と `session_id` を一致させる（entry ID のみで同じ session と推測しない）。`session_entries_source` の provenance lookup は entry ID 主体のまま維持する。`readOwnerSessions()` は既存 owner filter を維持し、entry 取得も複合 identity で絞る。

## 変更対象ファイルと手順

1. **新規 `scripts/convert-issue568-session-identity.ts`**: 明示された sessions root 内の全 group DB を列挙。全 DB が schema v5 で、既存 entry に対応する session があり、移行先の `(agent_id,id)`/sequence に衝突がないことを先に read-only preflight。各 DB を個別の immediate transaction で v6 へ移す。`sessions` と `session_entries` を新 table にコピーし、entry の owner は旧 `sessions.id = session_entries.session_id` JOIN から取得する。両 table を rebuild し FK/index（既存 `sessions_agent_id_id`, `session_entries_session_id_id`, `session_entries_source` を含む）を作り直す。旧 entry 整数 ID を明示してコピーし、次の append で既存 ID より大きい値が採番されることを検証する。SQLite の `PRAGMA foreign_keys=OFF` は transaction 内では効かないため、必要な場合だけ transaction 開始前に切り替え、commit 後 ON に戻して `foreign_key_check` と `integrity_check` を行う。`PRAGMA user_version=6` は同一 transaction の最後に設定。途中失敗は稼働再開せず全 group DB をバックアップから復元。旧形式を runtime から自動移行しない。v6/混合 version の再実行は拒否する（移行スクリプトの安全性のみであり runtime 互換分岐ではない）。`scripts/convert-issue556-session-owners.ts` の独立 DB transaction と CLI パス引数のパターンを参照するが、旧 converter を変更しない。
2. **`src/agent/session.ts`**: `SCHEMA_VERSION=6`、新規 DB の DDL/索引を更新。既存 v5 は通常起動時に拒否（現行 version check のまま）。`loadMessages`, `appendMessage`, `renameSession`, `readOwnerSessions` と、session の存在/競合判定・source dedup・entry append を複合 identity で行う。`readConversations` は global な entry ID により参照を解決したうえで同一 owner/session に属する pair だけ返す。外部 locator `sessionConversationPath` は既存 Main 用文字列を維持（Bot の同名 session を区別する locator の新設は今回不要）。明示 owner が必要な既存 Bot Task 経路を引数で通し、Main の呼出しは `main` を使う。単独 `id` のみで row を選ぶ SQL を残さない。owner 不一致で既存 session の owner を暗黙に書き換えない。
3. **`src/queue/bot-task-sessions.ts`**: `prepareBotTaskSession()` の `input.botId` を append 時に引き続き使用し、`loadBotTaskSystemPrompt()` の呼出しに保存済み Bot ID を渡す。**`src/queue/poller.ts`**: 既存 Bot Task の snapshot と trajectory 読取で `msg.botId` を session store に渡す。cron/no-Bot の読取は `main`。Bot の新規実行意味や queue ID は変更しない。
4. **`src/agent/manager.ts`, `src/sandbox/agent-runner.ts`, `src/sandbox/session-bootstrap.ts`, `src/sandbox/steering.ts`**: 現在 Runner payload（`src/sandbox/agent-runner.ts` の Zod schema）には owner ID がなく、`systemPromptSnapshotPresent` は Bot owner の証明にならない。`sendMessage()` の options に保存済み実行 owner を明示して Runner payload へ伝える。poller の既存 Bot Task は `msg.botId`、通常 Main は `main` を渡す。Runner の read/append/bootstrap/steer を同じ owner に固定し、Bot ID を group の Discord bot client ID と取り違えない。`runAgentLoop()` の呼出し元・sandbox 内部の追加 append 箇所も同じ owner を通す。Bot の新規実行意味や queue ID は変更しない。
5. **`src/discord/intake.ts`**: appendUserOnly の既存 `appendMessage()` は Main owner であることを明示。**`src/cron/session-retention.ts`**: cron per-run の作成と削除 SQL を `(main,id)` identity に合わせる。削除対象は従来どおり `kind='cron-per-run'` かつ期限超過のみ。**`src/queue/delivery.ts`**: item-thread の rename/rollback 呼出しに Main owner を明示し、既存の runtime `jobs.session_id` と `conversation_path` 更新の順番・補償を変えない。**`src/queue/poller.ts`** の `markEphemeralCronSession` 呼出しも Main とする。
6. **`src/memory/export.ts`**: export eligibility は変更しない。`readConversations()` の pair 解決結果と `source_json IS NOT NULL` 条件が変わらないことをテストで保証する。**`docs/storage.md`, `docs/spec/entity-model.md`, `docs/spec/cron.md`**: session v6 identity、停止時 migration、現行 Main cron と通常会話の共有履歴維持、変更しない queue/delivery 境界を更新。説明が変わる場合のみ `docs/agent-memory.md` の entry 参照節を調整。`config/cron.json` は変更しない。

実装前に同名 API の全 caller（`rg 'loadMessages\(|appendMessage\(|renameSession\(|readConversations\(|readOwnerSessions\(' src scripts`）を一巡し、テスト内 caller と `src/sandbox/session-bootstrap.ts` の複数 append 箇所も漏らさない。必要な引数順変更は一つの規則に統一し、optional `agentId=main` のまま owner を忘れる状態を避ける。`src/agent/manager.ts` から Runner への owner フィールド追加を忘れない。既存 bot task metadata（runtime DB）の保存形式は変えない。

## テスト

- **新規 `scripts/convert-issue568-session-identity.test.ts`**: v5 fixture に Main 通常会話+cron の同一 ID、別 Bot Task session、複数 entry、source JSON、未削除の採用参照に相当する整数 entry ID を入れる。変換前後で session/entry 数、owner、各 entry ID/sequence/payload/source、FK、version、entry 自動採番、rename の参照安定性を比較。無効 version と欠損参照は変更前に停止、再実行拒否を確認。runtime DB は変換しない。
- **`src/agent/session.test.ts`**: 既存 Main load/append/rename と source dedup、Bot Task の既存 owner 保存・読取、FK cascade と entry ID 不変を確認。owner の異なる同名 ID を通る新しい本番経路は作らない（#565）。
- **`src/memory/export.test.ts`, `src/queue/poller.test.ts`, `src/queue/poller.item-thread.integration.test.ts`, `src/queue/bot-task-sessions.test.ts`, `src/cron/session-retention.test.ts`**: 既存 entry ID pair の export 対象/非対象、cron の旧 session semantics、Bot Task snapshot 読取、期限切れのみ削除と late rename の回帰を確認。存在する test fixture に絞り、重複するテストを増やさない。

## 品質・運用確認

ルート `CLAUDE.md` に独立した「品質管理の実行手順」節は存在せず、`AGENTS.md` に委譲されている。編集した Biome 対象ファイルは直後に `pnpm exec biome check --write <file>`。完了前に `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test` を実行し、必要なら `pnpm build` と sandbox Runner image build も行う。文書更新は `.pi/skills/update-docs/SKILL.md` に従う。

ロールアウトは旧 worker/Runner を停止し書込が止まったことを確認、runtime DB と全 group session DB を SQLite 整合バックアップしてから version・件数を照合し、同じ checkout の converter を一度だけ実行。全 group DB の `foreign_key_check`, `integrity_check`, v6、owner 別 session/entry 件数、採用 entry ID 解決を検証後、同じ checkout の Host と Runner image を更新して起動。失敗時は停止を維持し、**全 group DB と runtime DB を一組として**バックアップへ戻す。旧/new プロセスを同じ DB に並走させない。既存 queue state は書換えない。実 DB の調査は `.pi/skills/runtime-db/SKILL.md` に従い read-only を原則とする。

## 使用 API と一次情報

現環境 `pnpm list better-sqlite3 --depth 0` は **12.11.1**。既存コードで使用中の `new Database(path, { readonly: true, fileMustExist: true })`, `db.pragma(...)`, `db.prepare(...).all()/get()/run()`, `db.transaction(fn).immediate()`, `db.close()` を再利用する。better-sqlite3 公式 API: https://github.com/WiseLibs/better-sqlite3/blob/v12.11.1/docs/api.md 。SQLite の table rebuild と FK 操作は https://www.sqlite.org/lang_altertable.html と https://www.sqlite.org/foreignkeys.html 、`PRAGMA user_version`, `foreign_key_check`, `integrity_check` は https://www.sqlite.org/pragma.html 、AUTOINCREMENT/`sqlite_sequence` は https://www.sqlite.org/autoinc.html を参照。`pnpm exec tsx` は既存 `scripts/convert-issue556-session-owners.ts` の実行方式を踏襲し、新規依存は追加しない。これら一次情報の URL は計画作成時に到達確認済み。
